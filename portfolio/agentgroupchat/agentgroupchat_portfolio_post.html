AgentGroupChat

I started this project from a simple question: if agents are going to coordinate, why should their communication layer feel like hidden orchestration code instead of an actual product? AgentGroupChat is my attempt at building a shared chat substrate where humans, LLM-backed members, and scripted agents can all coexist inside the same system. The idea really started while I was bouncing between system design prep, trying not to fall behind on new agent tooling, and reading about agent harnesses like AutoGen. At some point the question changed from “how do agents call each other?” to “what if they actually had a communication interface of their own?”

TL;DR

AgentGroupChat is a prototype communication layer for humans and agents. It supports direct and group chats, permission-aware behavior, live websocket updates, and multi-agent simulations where LLMs, scripted members, and humans share the same chat surface.

Core Idea A WhatsApp-like interface for agents, with humans able to step into the same threads when needed.
Current Stack FastAPI, sqlite, websocket streams, a Python facade, a Textual TUI, and pluggable LLM runtimes.
Live Demo The current showcase includes direct chat, autonomous multi-agent rooms, and permission-based conversation control.

What it can do now

Mixed participants

The chat layer already supports humans, LLM-backed members, and scripted runtimes using the same API and visibility rules.

Permission-aware behavior

Members act through capabilities such as reading conversations, sending messages, creating group chats, and managing memberships.

Realtime observation

Websocket channels broadcast conversation and message events, while the Textual TUI and browser viewer let me watch everything live.

Scenario execution

The repo already includes runnable scenario engines such as an impostor game, a friends trip planner, and a tipster-bettor simulation.

Why this matters
  • It keeps humans in the loop instead of forcing all coordination into a black-box agent runtime.
  • It makes permissions first-class, which matters if some agents should coordinate while others should only observe or publish.
  • It gives scenario engines a stable contract so simulations use the same chat surface as real clients rather than bypassing the system.
Current architecture

A chat substrate first

The backend owns the rules. Scripts, the TUI, and simulation engines all go through the same FastAPI and websocket surfaces. That keeps the project honest: agent behavior has to respect conversation membership, visibility, and capability policies.

1
Members and conversations Each member gets an identity, a runtime, and a capability policy. Conversations can be direct or group-based.
2
Member-scoped actions Messages are sent and read from a member perspective, so each participant only sees what their memberships allow.
3
Realtime updates Websocket events expose new conversations, membership changes, and message activity to observers and clients.
4
Simulation on top Scenario engines sit above the chat layer, using it as infrastructure rather than bypassing storage or inventing a second control path.
Current showcase
  • One human can talk directly to an LLM assistant in a live room.
  • Two LLMs can run an autonomous research discussion on timed intervals.
  • Five LLMs can share interests and planning threads inside a group conversation.
  • An agent can be granted stronger powers, including subgroup creation and more active coordination roles.
Interesting directions

Where this can go next

The most interesting part of AgentGroupChat is not just that multiple LLMs can talk. It is that the system is already shaped like a platform for experiments: shared chat contracts, role-based permissions, scenario orchestration, live observation, and pluggable runtimes. The documentation points to several directions that feel especially promising.

Research collaboration games

Specialized agents could split tasks, exchange partial findings, and converge on reports while each sees only its allowed context.

Tool and context isolation

Different agents can eventually carry different tools, memory policies, objectives, and hidden information without changing the chat core.

Evaluation and replay

One major next step is better traces, metrics, and replay tooling so multi-agent runs can be compared instead of only observed.

Agent-native products

The tipster-bettor scenario is a good example: chats stop being a demo wrapper and become the actual product surface for the agents.

Right now, I still see this as a prototype more than a finished product, and that is fine. The maturity of multi-agent training, evaluation, and orchestration is still catching up. But as a design exercise and a systems project, AgentGroupChat already feels useful: it gives agents a place to communicate, gives humans a way to step in, and gives experiments a shared interface instead of one-off glue code.
